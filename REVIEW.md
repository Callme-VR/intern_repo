# REVIEW.md

Defects found in the starter `app/main.py` (helpers, endpoints, models, and concurrency).

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (lines 72-74) | Returns `{"status": "ok"}` unconditionally without testing database connectivity. | Stop MongoDB or provide an invalid connection string; endpoint still returns 200 instead of 503. | Wrapped `db.command("ping")` in `try...except`, raising `HTTPException(503, "Database unavailable")` on failure. |
| 2 | `compute_late_minutes` (lines 33-37) | Checks `minutes > 10` after integer floor division of elapsed seconds by 60. | For shift `09:30` and punch-in `09:40:01`, elapsed is 601s -> `int(601/60) = 10`, then `10 > 10` is False, returning 0 instead of 10. | Computed `diff_sec = int((punch_in - start_dt).total_seconds())`, checking `diff_sec > 600`, then returning `diff_sec // 60`. |
| 3 | `compute_late_minutes` (lines 33-37) | Uses `punch_in.replace(hour=h, minute=m)` without anchoring to `attendance_date`. | In overnight shifts (e.g. 22:00 to 06:00), punch-in past midnight (e.g. 02:00) sets `start` on the current calendar day instead of the previous day's shift start, resulting in negative/zero late minutes. | Anchored `start_dt` to the resolved `attendance_date` in IST. |
| 4 | `compute_work_hours` (lines 40-41) | Uses Python's built-in `round()`, which performs round-half-to-even (banker's rounding) instead of half-up (R4, R8). | Difference of 7650 seconds = 2.125 hours; `round(2.125, 2)` gives `2.12` instead of required `2.13`. | Used `Decimal` with `ROUND_HALF_UP` on total seconds divided by 3600. |
| 5 | `compute_overtime` (lines 44-47) | Missing the 30-minute minimum threshold check mandated by Rule R3. | Punch-out 15 minutes after shift end returned 15 instead of 0. | Added threshold check: return `minutes` if `minutes >= 30` else 0. |
| 6 | `compute_overtime` (lines 44-47) | Does not handle overnight shifts (`shift_end <= shift_start`). | For a 22:00–06:00 shift, `shift_end` was placed on `date_str` instead of `date_str + 1 day`, computing massive negative or false overtime. | Added check: if `shift_end <= shift_start`, advance `shift_end` datetime by one calendar day. |
| 7 | `create_employee` (lines 78-85) | Check-then-insert race condition (`find_one` followed by `insert_one`). | Two concurrent `POST /employees` requests with identical `emp_code` both pass the check and create duplicate records. | Backed by unique index on `emp_code` and handled `DuplicateKeyError` to return HTTP 409. |
| 8 | `create_employee` (lines 78-85) | `created_at` set using naive `datetime.now()` and returned as an unformatted datetime rather than epoch milliseconds. | Returned payload violates OpenAPI schema (`EpochMillis` integer). | Saved UTC datetime truncated to seconds and serialized to epoch milliseconds integer. |
| 9 | `create_employee` / `EmployeeIn` (lines 53-61) | Missing input validations: didn't enforce `shift_start != shift_end`, email format, or `emp_code` pattern `^EMP\d{4,6}$`. | Creating an employee with `shift_start == "09:30"` and `shift_end == "09:30"` succeeded with 201 instead of 422. | Added Pydantic field regex patterns, length constraints, and model validator ensuring `shift_start != shift_end`. |
| 10 | `list_employees` (line 93) | Incorrect pagination offset calculation `skip = page * page_size`. | For `page=1, page_size=20`, `skip = 20`, completely skipping the first 20 records on page 1. | Corrected offset formula to `skip = (page - 1) * page_size`. |
| 11 | `list_employees` (line 94) | `total` count always counts all documents (`count_documents({})`), ignoring the `department` filter (violates R10). | Filtering by department returned the whole collection's document count in `total`. | Changed count query to `db.employees.count_documents(q)`. |
| 12 | `list_employees` (line 95) | Missing sort order; contract specifies sorted by `emp_code` ascending. | Employees returned in arbitrary MongoDB natural order. | Added `.sort("emp_code", 1)` to the query. |
| 13 | `punch_in` (lines 100-105) | Did not check if the employee exists before punching in. | Sending an unknown `emp_code` resulted in `emp` being `None`, raising unhandled `TypeError` (HTTP 500) when accessing `emp["shift_start"]`. | Added check: `if not emp: raise HTTPException(404, "Employee not found")`. |
| 14 | `punch_in` (lines 100-105) | Check-then-insert race condition (`find_one` followed by `insert_one`). | Two simultaneous punch-in requests for the same date both pass `find_one` and insert duplicate attendance documents. | Backed by unique compound index on `(emp_code, date)` and caught `DuplicateKeyError` returning HTTP 409. |
| 15 | `punch_in` (lines 118-121) | Injected `id = str(res.inserted_id)` into response document. | Contract and `DATA_MODEL.md` explicitly state attendance records have no ID (natural key is `(emp_code, date)`). Injected `id` fails schema validation. | Removed `id` field and serialized strictly according to `AttendanceRecord` schema. |
| 16 | `punch_in` (lines 102-103) | Did not implement overnight shift attendance date calculation (R1). | For overnight shift 22:00–06:00, a punch-in at 02:00 AM IST was assigned today's date instead of previous day's shift date. | Implemented `get_attendance_date` adjusting overnight early morning punches to the previous day. |
| 17 | `list_attendance` (lines 144-147) | Unscalable in-memory loading: `list(db.attendance_logs.find(q))` fetched all documents into Python memory before sorting and slicing. | Querying with 100,000 records consumes high memory and risks timing out. | Executed `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)` directly in MongoDB supported by compound indexes. |
| 18 | `list_attendance` (lines 125-132) | Missing validation for `date_from > date_to`. | Passing `date_from=2026-07-10&date_to=2026-07-01` returned an empty list with 200 instead of HTTP 422. | Added validation `if date_from and date_to and date_from > date_to: raise HTTPException(422)`. |
| 19 | `punch_out` | Non-atomic update allowed concurrent punch-outs to race. | Two simultaneous `POST /attendance/punch-out` requests both read open status and returned 200. | Used atomic `find_one_and_update({"_id": record["_id"], "punch_out": None}, ...)` returning 409 if already modified. |
| 20 | `punch_out` | Missing timestamp interval validation. | Supplying `punched_at <= punch_in` or `> 24 hours` after punch-in was accepted or misclassified. | Added explicit validations raising HTTP 422 when `punched_at <= punch_in` or `diff_sec > 86400`. |
| 21 | `punch_out` | Writing to `history` on punch-out. | Punch-out added an entry to `history`, violating the contract rule that `history` is reserved strictly for manual corrections. | Removed history modification from punch-out; `history` is now only modified in `PATCH /attendance/{emp_code}/{date}`. |
| 22 | `regularize_attendance` | Accepted punch times when setting status to `ABSENT` or `LEAVE`. | Passing `{"status": "ABSENT", "punch_in": ...}` updated the record instead of failing validation. | Added validation: if target status is `ABSENT` or `LEAVE` and `punch_in` or `punch_out` is provided, raise HTTP 422. |
| 23 | `regularize_attendance` | Allowed no-op requests to succeed. | Sending a regularization payload that changed no values returned 200 with an empty history entry. | Added check comparing old and new fields; raises HTTP 422 ("Request changes nothing") if `changes` dictionary is empty. |
| 24 | `regularize_attendance` | Race condition in concurrent regularization updates. | Simultaneous edits could overwrite each other's history entries. | Implemented optimistic concurrency lock checking current history length `{"history": {"$size": cur_len}}`, returning 409 on conflict. |
| 25 | Pydantic Request Models | Permissive coercion of floats, booleans, and strings for timestamp fields. | Passing a float or string formatted instant was coerced instead of rejected. | Added `strict=True` to `EpochMillis` integer fields to strictly enforce int types (HTTP 422 on strings/floats). |

---

### Non-defects examined:
- **`IST` timezone definition (`timezone(timedelta(hours=5, minutes=30))`):** Verified that IST offset is strictly UTC+05:30 with no daylight saving shifts; defining it via standard `timedelta` is correct and lightweight.
- **Pydantic default values for shifts (`09:30` / `18:30`):** Matches default values specified in OpenAPI schema.
- **Pydantic extra fields behavior:** Confirmed that client-sent derived fields (`work_hours`, `late_minutes`, etc.) must be ignored rather than rejected with 422, matching default Pydantic behavior.
